# Evaluation protocol

1. Create a live financial or e-commerce project, declare its use case/entity/jurisdictions and finalise its source/answer revision. The New Project form offers nine fictitious financial cases; adapt them to representative anonymised institution workflows.
2. Before running extraction, independently annotate expected requirements, ambiguity/conflict labels and acceptable lifecycle alternatives. Record a conventional manual baseline and timing under the same conditions.
3. In Evaluation, create a reference dataset with stable gold IDs, statements, labels, acceptable lifecycle models and methodology notes.
4. A distinct architect and product-owner account review the reference. The author cannot adjudicate their own dataset. Both approvals must predate inference for research eligibility; merely creating the reference before inference is insufficient.
5. Run the real configured model. Retain source, code/model revision, exact masked prompts, responses, repairs, failures, processing time and output digest.
6. Reviewers provide one-to-one extracted-to-gold matches, citation/claim support judgments, requirement correctness/corrections and stakeholder satisfaction scores. Use the frozen reference dataset ID in annotations.
7. Submit the annotations to compute metrics. IDs must exist and duplicate matches cannot inflate scores. Human-reviewed provenance requires an adjudicated reference for the exact input; empirical eligibility additionally requires a live run and a reference created before inference.
8. Repeat cases/runs, preserve failures, adjudicate disagreements and compare per-case results with the manual baseline. Report sample sizes and uncertainty. Group labels can support stratified bias analysis.

Implemented metrics: extraction precision/recall/F1 and reference completeness; ambiguity/conflict precision/recall/F1; citation support accuracy and judged coverage; unsupported-claim rate; requirement correctness, reviewed consistency and correction rate; reviewer-verified applicable-control coverage; verified traceability plus separately labelled structural links; agreement with any expert-accepted lifecycle; processing/manual time and difference; mean satisfaction; Brier score and calibration bins for self-assessed confidence. Optional `consistency`, `controls` and `traceability` annotation arrays accept actual reviewer judgments and validate referenced IDs. Empty judgment sets remain unmeasured.

Null means not measured. An empty citation/claim/satisfaction judgment set is not perfect performance. Fixture runs are labeled authored tests and never establish model effectiveness. Model confidence remains self-assessment; diagnostic calibration metrics require actual correctness annotations and do not automatically recalibrate the model.

The financial case catalogue covers banking, lending, payments, fraud detection, insurance, investment operations, regulatory reporting, onboarding/KYC and analytics. `npm run analyse -- --case lending` runs a real model against a selected fictitious brief. `npm run benchmark -- --limit 1` runs a bounded number of cases and records completed/failed runs and artifact paths; it requires a reachable model and creates no fabricated gold labels, manual timings or satisfaction scores. Use the authenticated project workflow to freeze independent references before inference.

Project and accessible-project study summaries are available through Evaluation and `/api/projects/:id/study` / `/api/study`. They exclude fixtures, controlled tests, unverified legacy runs and unadjudicated evidence; corrected annotations supersede earlier annotations for the same case/version. Descriptive means include measurement counts and preserve nulls. Repeated runs may be correlated; the summary does not assert confidence intervals or causal improvements. No precision/recall, hallucination reduction, time-saving or satisfaction result is claimed from the controlled test suite.
